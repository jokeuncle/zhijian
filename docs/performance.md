# 性能验收

2026-11-15，本机 macOS 26.4.1 / Apple M5 / 24 GB / arm64 / Swift 6.3.2，release 构建。数据来自独立临时词库，10,000 条合成概念，包含中文解释、英文名、别名和长正文，SQLite 主文件约 65.35 MB。导入也写入首次变更快照与搜索索引。测试结束后删除临时库，未向用户词库写入测试数据。

命令：`scripts/zhijian benchmark --count 10000`。延迟测量在已启动的同一 CLI 进程内执行，每类读取 40 次，P95 按样本排序取值；不包含 GUI 动画、160 ms 输入防抖或进程启动成本。原始结果见 [performance.json](performance.json)。这是当前机器上的有限样本，不是所有硬件或数据分布的上限保证。

| 操作 | 中位数 | P95 |
|---|---:|---:|
| 首页 60 条摘要，含总数 | 5.98 ms | 6.89 ms |
| 英文检索 `Concept 932` | 0.37 ms | 0.42 ms |
| 中文索引检索 `传送带` | 28.48 ms | 33.31 ms |
| 两字中文检索 `隐状` | 29.17 ms | 36.89 ms |

10,000 条批量导入 **676.54 ms**；重开数据库 **3.02 ms**。另一轮相同规模测试导入为 613.82 ms、短中文 P95 为 54.33 ms，说明系统负载会影响尾延迟。

初始 20 词条的原生主窗口在一次空闲快照中 RSS 为 125,904 KiB（约 123 MiB）、CPU 为 0.0%。这是进程的单次快照，不是峰值内存或能耗分析。

另用独立的 10,000 条合成词库启动实际原生窗口，并打开含全部 10,000 个成员的阅读集。辅助功能树实际只出现 **24 个**进度跳转按钮；界面显示总数 10,000，列表仍按 60 条摘要分页。该次稳定窗口快照 RSS 为 89,296 KiB（约 87.2 MiB），CPU 为 0.0%。不同进程启动及系统压缩状态会影响 RSS，这两次观察不能当作内存随数据量下降的结论。

## 已采用的边界

- 词库使用 SQLite WAL、prepared statements 和导航索引。已有 schema 的打开路径跳过迁移与写事务，避免只读客户端抢写锁。
- 常规列表默认 60 条，最多 200 条；只取摘要列。完整词条在选中后才解码，备份导出是明确的全库操作。
- 搜索防抖 160 ms，查询在主 actor 外执行，旧查询与旧选择的结果不会回写覆盖新状态。
- FTS5 trigram 为三字及以上的子串检索提供索引。少于三字的中文使用子串回退；它需要扫描搜索文本，因此单独测量。相关原理见 [SQLite FTS5 文档](https://www.sqlite.org/fts5.html)。
- 批量导入使用单个事务；整个输入的内容与关联在提交前验证。FTS 按 rowid 更新，避免按未索引 ID 逐条扫描造成二次方导入开销。
- 每次打开词条只写独立的最近阅读时间，不重建全文索引或创建内容历史。
- 外部 Agent 修改通过活动窗口中的轻量 `data_version` 检查发现；每 2 秒一次，窗口不活动时跳过。已经在真实应用中观察到独立 CLI 改动后自动刷新。
- 核心行为检查覆盖分页无重叠、独立连接可见性、原子导入、版本冲突和复习持久化；真实子进程验证 CLI/MCP 共享同一词库。

尚未进行长时间泄漏 / 能耗分析、100,000 条以上压力测试或 Intel 机器实测。
